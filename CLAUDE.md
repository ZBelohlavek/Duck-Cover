# Duck and Cover: notes for Claude

An original 5v5 attack-and-defend shooter in Unity 6 (6000.3, URP). Attackers plant a defuser on one
of two charges; walls broken in one round stay broken for the whole match, sides swap every round,
and eliminated players keep helping through the Backline (cameras, scout bots, pings, support
actions). Heroes with abilities come after the base game. The name, teams, maps, characters and
devices are our own: never copy another game's operators, maps, gadget designs or interface.

The plan, with the rules, the contracts and the work packages, is the Claude Doc
https://claude.ai/artifact/JJ4fD74nbDB3AsykT2WWen. `docs/ROADMAP.md` tracks which packages are done.
The owner gives tasks in plain language. Build them, check your own work (see "Verifying changes")
and fix what you find before reporting back.

## Layout

```
Assets/DuckAndCover/
  Scripts/Core/   Game rules in plain C# (asmdef DuckAndCover.Core, noEngineReferences). Runs in Tests/CoreSim.
          Common/     Vec3, TeamId, Side, SiteId
          Contracts/  IWorldQuery, INetBridge, MatchCommand, IAbility, ISupportAction, IGameEvents
          <Module>/   Match, Ruleset, Destruction, Breach, Objective, Combat, Backline, Abilities (one folder each)
  Scripts/Net/    The only code that touches Netcode for GameObjects (asmdef DuckAndCover.Net)
  Scripts/Game/   Player, weapons, surfaces, devices, objective, map components; GameBootstrap,
                  ScreenshotDirector, CaptureRequest (asmdef DuckAndCover.Game)
  Scripts/UI/     HUD, scoreboard, pick and prep screens, Backline view, built in code (DuckAndCover.UI)
  Editor/         "Duck and Cover" menu, automation, scene setup, map validator (DuckAndCover.Editor)
  Data/           Ruleset, loadouts, abilities, map definitions
  Scenes/         Boot (generated by Editor/SceneSetup.cs)
Tests/CoreSim/            Rule tests ([Test] methods, one file per module under Tests/) and reports
Tests/UnityCompileCheck/  Compiles all Unity scripts against stubs of the Unity, Editor and Netcode APIs
Tools/unity.ps1, unity.sh Runs real Unity from the command line: check, capture, scenes
docs/ROADMAP.md           Work packages and their status
```

Assembly references go one way: Core <- Net <- Game <- UI, and Editor sees them all. Core references
nothing. If Game needs something from UI, raise an event instead of adding a reference.

## Rules

- **Core stays engine-free.** Nothing in `Scripts/Core` may use UnityEngine, UnityEditor or Netcode.
  The asmdef enforces it in Unity and `ContractTests.CoreHasNoEngineReferences` in the cloud. Put rules
  in Core and keep Unity code thin: it sends player commands down and draws events and state that come
  back. Convert vectors at the boundary with `VecExtensions` (`ToVec3`, `ToVector3`).
- **The server decides.** Clients send `MatchCommand`s (requests), never results. Every outcome
  (damage, destruction, budgets, objective) is decided by Core on the host or server.
- **Contracts are shared.** The interfaces in `Core/Contracts` are what packages build against in
  parallel. Change a signature only when your package needs it, and say so in the pull request.
  `MatchSnapshot`, `AbilityContext` and `SupportContext` are partial: add your module's fields in a new
  file in your module folder (for example `Core/Destruction/MatchSnapshot.Destruction.cs`) rather than
  editing the contract file.
- **Numbers live in the ruleset**, never as literals in rules code, so balance can change without code.
- **Deterministic rules.** Core uses no wall clock and no `System.Random` without a seed: time comes in
  through `Tick(dt)` and randomness from a seeded generator, so tests and both network copies agree.
- **C# 9.** That's what Unity compiles. No file-scoped namespaces, `record struct`, `required`, or
  global usings.
- **Only Net touches the network library.** Game and UI go through Net's own types and `INetBridge`.
- **UI is code.** No prefabs for screens. Use `UITheme` colours. Team colours follow the team, not the
  side, because sides swap every round.
- **Unity pitfalls:**
  - Don't use `??` or `?.` on UnityEngine objects (destroyed objects aren't really null); use `== null`.
  - Don't name a method `Start(...)` or `Update(...)` with parameters.
  - `Object.Destroy` is deferred to the end of the frame.
- **Scenes.** Boot is generated: edit `Editor/SceneSetup.cs` and rerun it (`Tools/unity.ps1 scenes` or
  the menu **Duck and Cover > Rebuild Scenes**) rather than editing it by hand. Maps (WP9 on) are laid
  out in the editor and committed; SceneSetup never touches them.
- **Meta files.** Commit a `.meta` beside every new file and folder under `Assets/`. Keep GUIDs stable;
  scenes reference scripts by GUID.
- **Paid assets:** never commit imported or extracted pack files (`Assets/Synty/`, `Assets/ThirdParty/`,
  or FBX/PNG exported from paid Unreal packs). Pack archives go in `AssetPackages/` through Git LFS, and
  the repo stays private. Free assets must be CC0 or allow commercial use, with the licence file beside
  them.

## Verifying changes

Run these in order and fix failures before reporting.

1. `dotnet run --project Tests/CoreSim`: must end with `ALL CHECKS PASSED`. Add tests for every rule you
   write. `dotnet run --project Tests/CoreSim -- Match` runs only tests whose name contains "Match".
2. `dotnet build Tests/UnityCompileCheck`. It uses stubs, so if you call a Unity, Editor or Netcode API
   that isn't stubbed yet, add it to `UnityStubs.cs` with the real signature. Don't invent APIs to make
   the build pass. The stubs don't enforce asmdef boundaries, so check references by hand.
3. Real Unity (needs the editor **closed**, runs on the owner's Windows PC):
   - `Tools/unity.ps1 check` (Windows) or `Tools/unity.sh check`: a real compile. It lists any
     `error CS` lines.
   - `Tools/unity.ps1 capture`: plays the Boot scene and writes `Screenshots/*.png` plus
     `Screenshots/log.txt`, which lists every warning and error from the run. **Look at the PNGs** and
     read log.txt. The exit code is 1 if anything logged an error.
4. If the Unity editor is open and a Unity MCP server is connected, use it instead of step 3: read the
   console, run **Duck and Cover > Capture Screenshots**, then open the PNGs in `Screenshots/`.

When you add a screen or a scene worth checking, add a shot to `ScreenshotDirector.Shots()`.

## Setup facts

- Unity 6000.3 (`ProjectSettings/ProjectVersion.txt`), URP 17.3, Input System only (the old Input
  Manager is off), Netcode for GameObjects 2.13. Unity Relay sessions come with WP3.
- The project-wide input actions are `Assets/InputSystem_Actions.inputactions` (Unity's default set).
- The project is not linked to a Unity Cloud project yet. Relay needs that; link it in
  Project Settings > Services when WP3 starts.
